# v0.1.0 capacity evidence

This report records workload-specific, single-host measurements for release
candidate `58326ec93c088f1e64f7ce8b89faff96c010b1c8`. It is reproducible evidence,
not an SLA or a production sizing promise.

## Method

- Host: Windows 11 with Docker Desktop, Docker Engine 29.8.2, Compose 5.5.1.
- Services: MySQL 8.4.11, Redis 7.4.11, API, worker, and a local Webhook sink.
- Limits: API/worker 2 CPU and 512 MiB each; MySQL 2 CPU/1.5 GiB; Redis 1
  CPU/512 MiB; sink 1 CPU/256 MiB.
- Input: 86 payloads from seven event types in the commit-pinned Octokit
  Webhooks fixture archive. The archive and k6 image digests are in
  `capacity/lock.json`; measurement is offline after preparation.
- Load: constant 8 events/s for 20 seconds, three isolated repetitions per
  worker-concurrency setting, with fresh volumes and dynamic host ports.
- Accepted throughput is k6 accepted requests divided by test duration.
  Accepted P95 measures HTTP admission latency. Completion throughput is
  completed workflow runs divided by first-create to last-finish time.
  Completion P95 measures event admission to terminal workflow completion.
- Run with `capacity/run.ps1`; raw results are intentionally excluded from Git.

## Normal-load matrix

Throughput is the median of three runs; P95 is the worst P95 from those runs.
Accepted and completion throughput CV remained below 10% for every setting.

| Worker concurrency | Accepted events/s | Accepted P95 | Completion runs/s | Completion P95 | Accepted CV | Completion CV |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 7.999 | 138.8 ms | 3.358 | 28.849 s | 0.20% | 4.83% |
| 4 | 8.031 | 126.0 ms | 3.952 | 20.445 s | 0.09% | 1.34% |
| 8 | 8.029 | 141.6 ms | 4.211 | 22.236 s | 0.23% | 6.45% |
| 16 | 8.023 | 887.7 ms | 4.692 | 16.750 s | 0.21% | 5.34% |

All runs completed 160 or 161 accepted events. The offered rate exceeds the
observed completion rate, so queues grew during the 20-second load window and
drained afterward. Concurrency improved drain throughput, but the 16-worker
admission P95 outlier and diminishing gains show that more goroutines are not a
free scaling mechanism. This run does not establish saturation capacity.

## Queue recovery

Both recovery scenarios used 4-worker concurrency, 8 events/s for 10 seconds,
and three repetitions. Backlog recovery stopped the worker during admission.
Crash recovery killed the worker in flight, waited 62 seconds for the fixed
60-second outbox lease to expire, then restarted it.

| Scenario | Completed per run | Drain seconds | Completion P95 |
|---|---:|---:|---:|
| Backlog | 80 / 81 / 81 | 22.510 / 22.890 / 23.162 | 17.658 / 18.191 / 21.612 s |
| Crash | 80 / 81 / 81 | 18.221 / 18.222 / 18.697 | 76.376 / 76.760 / 77.279 s |

Every accepted event reached a terminal state. Crash recovery is at-least-once:
an expired processing item can be delivered again after lease expiry, so the
receiving Webhook still needs idempotency. The measured 60-second lease is also
the dominant recovery-time floor; this project does not claim exactly-once.

## Known limits

- The 20-second load window is regression evidence, not a soak test or a basis
  for production SLO, autoscaling, RPO, or RTO commitments.
- The test does not cover multi-host workers, MySQL/Redis failover, network
  partitions, slow third-party Webhooks, or high-cardinality tenant mixes.
- One seeded workflow and a local sink do not represent every DAG shape,
  payload size, retry pattern, or external API rate limit.
- Lower crash recovery time requires a lease/heartbeat design change and new
  correctness tests; shortening the benchmark wait would not prove recovery.
